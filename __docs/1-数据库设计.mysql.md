# 基于多人协同的高校固定资产管理系统（FAMS）MySQL数据库设计文档（优化版）
## 文档基础信息
- 项目名称：基于多人协同的高校固定资产管理系统(FAMS)
- 课程：企业项目综合实训（一）
- 数据库：MySQL 8.0+
- 存储引擎：InnoDB
- 字符集：utf8mb4
- 排序规则：utf8mb4_unicode_ci
- 设计规范：双ID设计（数字自增主键+32位字符串分布式biz_id）、软删除、全链路操作留痕、多级协同审批、多人协同盘点
- 本次优化方向：查询性能提升、数据一致性保障、业务扩展性增强、审计追溯能力完善

## 一、原有数据表方案评价与优化方案
### 1.1 原有表结构优点
1. 权限分层模型设计合理，用户/角色/权限多对多关联，适配校级管理员、学院管理员、普通师生三级权限隔离；
2. 业务模块拆分清晰，区分资产、部门、状态、关联中间表，低耦合；
3. 预留多角色、多部门关联设计，适配多人协同作业核心需求；
4. 双ID设计、软删除、全链路留痕的基础架构完善，满足分布式部署与审计要求。

### 1.2 原有表结构缺陷与修改建议
#### 原有核心缺陷修复（已落地）
1. **冗余中间表（用户-部门、资产-部门关联表）**
   用户、资产均只归属单一部门，属于多对一关系，无需中间关联表，直接在主表增加`dept_biz_id`字段即可，减少多表联查开销。
2. **资产状态关联表设计不合理**
   频繁修改资产当前状态会产生大量中间表数据，读写性能差；优化：通用字典表存状态枚举，资产表存储当前状态编码，新增**资产状态变更流水表**记录全量历史变更，满足审计追溯。
3. **统一登记表过于笼统**
   领用、归还、报修、报废、盘点属于完全独立业务流程，合并一张表会产生大量空字段；拆分独立业务单据表，搭配通用审批流表统一管理多级审核。
4. **维修工单必须独立建表**
   报修工单包含维修人、维修费用、故障描述、维修进度等专属字段，无法合并至通用登记表。
5. **资产发票、设备照片需独立附件表**
   资产与附件为一对多关系，单独附件表统一存储文件路径、类型、上传人，易于后期扩展采购合同、验收单据等附件。
6. **缺失强制要求的审计日志表**
   实训需求明确要求所有操作实名留痕、可追溯，需新增全局操作审计日志表。
7. **缺失多人协同盘点专用数据表**
   本实训两大重点：多级审批、多人协同盘点，需新增盘点任务主表、盘点明细录入表，支持多人同时录入盘点数据、LLM自动比对盘盈盘亏。
8. **缺少通用数据字典表**
   资产状态、审批结果、资产分类等枚举统一由字典表管理，便于后期维护扩展。

#### 新增深度优化点（本次补充）
9. **盘点明细缺失去重约束，多人协同易产生脏数据**
   原盘点明细表未限制单任务下单资产的重复录入，多人并行盘点时易出现重复记录。优化：新增`(task_biz_id, asset_biz_id)`联合唯一索引，保证单任务下同一资产仅保留一条有效盘点记录。
10. **高频查询未覆盖软删除字段，索引回表开销大**
    所有业务查询默认携带`is_delete = 0`过滤条件，原索引未包含该字段，会导致查询时回表过滤。优化：将高频查询索引升级为联合索引，统一纳入`is_delete`字段，提升查询性能。
11. **部门树形查询无索引，多级部门查询性能差**
    `sys_department`表的`parent_biz_id`字段无索引，递归查询部门树时随数据量增长性能衰减明显。优化：为`parent_biz_id`新增普通索引。
12. **审计日志缺失业务关联维度，单资产追溯困难**
    原审计日志仅支持按操作人、模块查询，无法快速追溯单条资产/单据的全生命周期操作记录。优化：新增`business_type`、`business_biz_id`字段，关联对应业务主体，满足精细化审计追溯需求。
13. **资产编号与分布式ID耦合，适配性不足**
    原`biz_id`同时承担分布式ID和资产业务编号的职责，无法适配高校现有固定资产编码体系（国资编号、条码号）。优化：资产表新增独立`asset_code`业务编码字段，与biz_id解耦，支持自定义编码规则。
14. **部分枚举字段硬编码，扩展性不足**
    `attach_type`、`business_type`、`perm_type`、`user_status`等字段采用硬编码值，新增类型需修改代码。优化：建议全部枚举值逐步纳入`sys_dict`字典表统一管理，通过编码关联，降低维护成本。
15. **冗余状态字段无一致性保障，存在数据不一致风险**
    审批流最终结果、单据状态等字段存在数据冗余，业务代码漏更新会导致数据不一致。优化：核心状态变更通过数据库事务保证同步更新，也可通过触发器实现自动联动，降低代码出错概率。

## 二、统一数据库设计规范
### 2.1 主键规范（双ID设计，支持分布式部署）
1. `id BIGINT AUTO_INCREMENT PK`：本地自增数字主键，用于单库快速关联查询；
2. `biz_id VARCHAR(32) NOT NULL UK`：分布式唯一业务ID，雪花算法生成，接口、报表、跨服务统一使用。

### 2.2 约束标识说明
- PK：主键
- UK：唯一索引
- NK：NOT NULL 非空约束
- DEF：字段默认值
- FK：外键关联字段（关联对应表biz_id）
- COMMENT：字段注释

### 2.3 时间字段统一规范
1. 通用创建时间：`create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`
2. 通用更新时间：`update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`
3. 业务专属时间：购置时间`buy_time`、申请时间`apply_time`、办结时间`finish_time`、盘点录入时间`check_time`、审批时间等。

### 2.4 软删除规范
所有业务主表统一增加字段：`is_delete TINYINT NOT NULL DEFAULT 0`，0=正常数据，1=逻辑删除，禁止物理删除，保障协同审计数据完整可追溯。

### 2.5 协同审计规范
所有业务操作、状态变更、盘点、审批记录均留存操作人`oper_user_biz_id`、操作时间，完整记录操作人员与操作行为，满足系统审计要求；审计日志支持按业务主体追溯全生命周期操作。

### 2.6 索引设计规范
1. 唯一索引优先保障业务唯一性约束（如biz_id、联合业务主键）；
2. 高频查询索引采用联合索引设计，默认纳入`is_delete`软删除字段；
3. 外键关联字段统一建立普通索引，提升联查性能；
4. 树形结构父级字段必须建立索引，优化递归查询。

#### 1.1 部门表 `sys_department`
存储学校、学院、实验室等多级部门信息
```sql
CREATE TABLE `sys_department` (
  `id` BIGINT AUTO_INCREMENT COMMENT '自增主键 PK',
  `biz_id` VARCHAR(32) NOT NULL COMMENT '部门分布式唯一ID UK NK',
  `dept_name` VARCHAR(64) NOT NULL COMMENT '部门名称 NK',
  `parent_biz_id` VARCHAR(32) DEFAULT '' COMMENT '上级部门biz_id，校级无上级',
  `dept_sort` INT DEFAULT 0 COMMENT '排序权重 DEF',
  `is_delete` TINYINT NOT NULL DEFAULT 0 COMMENT '软删除 0正常1删除 DEF NK',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间 NK DEF',
  `update_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间 NK DEF',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_dept_biz_id` (`biz_id`),
  KEY `idx_parent_biz_id` (`parent_biz_id`),
  KEY `idx_dept_is_delete` (`is_delete`)

```

## 四、关键业务问题专项说明
### 4.1 维修工单是否需要独立建表？
**必须独立建表`fams_repair_workorder`**
1. 工单存在专属业务字段：维修人员、维修费用、故障描述、维修结果、工单流转状态，无法与领用、报废单据合并；
2. 工单需接入多级审批流程，独立表便于状态流转、维修台账统计、报表导出；
3. 若合并至通用登记表会产生大量空字段，降低查询性能，不利于后期扩展维修结算、耗材管理功能。

### 4.2 资产发票、凭证图片如何存储？
采用独立附件表`fams_asset_attach`一对多存储：
1. 单个资产可上传多张采购发票、设备实拍、报修截图；
2. 统一管理文件存储路径、文件类型、上传操作人员；
3. 资产主表不存储大文件路径，减少主表查询开销，可灵活扩展采购合同、验收单等附件类型。

### 4.3 分布式biz_id生成方案
所有业务对外ID（用户、资产、部门、单据、附件）统一使用32位字符串biz_id，推荐雪花算法生成，全局唯一；
- 数字自增id：仅用于数据库内部快速关联查询；
- biz_id：接口请求、前后端交互、报表导出、分布式多服务数据同步统一使用。

### 4.4 系统时间字段设计覆盖场景
1. 通用基础时间：`create_time`创建时间、`update_time`更新时间（全表标配）；
2. 资产基础时间：`buy_time`资产购置日期；
3. 审批流程时间：`apply_time`申请时间、`finish_time`办结时间、`dept_audit_time`学院审批时间、`school_audit_time`校级审批时间；
4. 资产借用时间：`borrow_start_time`借用起始、`borrow_end_time`预计归还、`actual_return_time`实际归还；
5. 工单业务时间：`report_time`报修提交时间、`finish_time`维修完成时间；
6. 盘点业务时间：`start_time`盘点开始、`end_time`盘点截止、`check_time`盘点录入时间；
7. 审计追溯时间：`oper_time`全局操作时间、资产状态变更记录时间。
全部时间字段完整覆盖实训需求中资产入库、领用、多级审批、多人协同盘点、报修报废全业务流程时间追溯。

### 4.5 多人协同盘点的数据一致性如何保障？
1. 通过`(task_biz_id, asset_biz_id)`联合唯一约束，从数据库层面杜绝单任务下重复盘点同一资产；
2. 所有盘点录入操作记录操作人与时间，支持多人并行录入且权责清晰；
3. 盘点任务状态与明细数据变更建议通过事务提交，避免任务状态与明细数据不一致。

### 4.6 资产全生命周期操作追溯如何实现？
1. 审计日志新增业务关联字段，可通过资产biz_id快速检索所有相关操作记录；
2. 资产状态变更流水表完整记录状态变更轨迹；
3. 领用、报修、报废、盘点单据均关联资产ID，可串联资产从入库到报废的全流程单据。
