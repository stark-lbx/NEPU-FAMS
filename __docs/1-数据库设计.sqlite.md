# 文档二：SQLite 版本（优化版）
# 基于多人协同的高校固定资产管理系统（FAMS）SQLite数据库设计文档（优化版）
## 文档基础信息
- 项目名称：基于多人协同的高校固定资产管理系统(FAMS)
- 课程：企业项目综合实训（一）
- 数据库：SQLite 3.30+
- 字符集：原生支持UTF-8（兼容utf8mb4）
- 设计规范：双ID设计（数字自增主键+32位字符串分布式biz_id）、软删除、全链路操作留痕、多级协同审批、多人协同盘点
- 适配场景：Python单机实训项目开发、本地原型验证
- 本次优化方向：查询性能提升、数据一致性保障、业务扩展性增强、SQLite特性适配

## 一、原有数据表方案评价与优化方案
### 1.1 原有表结构优点
1. 权限分层模型设计合理，用户/角色/权限多对多关联，适配校级管理员、学院管理员、普通师生三级权限隔离；
2. 业务模块拆分清晰，区分资产、部门、状态、关联中间表，低耦合；
3. 预留多角色、多部门关联设计，适配多人协同作业核心需求；
4. 双ID设计、软删除、全链路留痕的基础架构完善，满足审计与功能扩展要求。

### 1.2 原有表结构缺陷与修改建议
#### 原有核心缺陷修复（已落地）
1. **冗余中间表（用户-部门、资产-部门关联表）**
   用户、资产均只归属单一部门，属于多对一关系，无需中间关联表，直接在主表增加`dept_biz_id`字段即可，减少多表联查开销。
2. **资产状态关联表设计不合理**
   频繁修改资产当前状态会产生大量中间表数据，读写性能差；优化：通用字典表存状态枚举，资产表存储当前状态编码，新增**资产状态变更流水表**记录全量历史变更，满足审计追溯。
3. **统一登记表过于笼统**
   领用、归还、报修、报废、盘点属于完全独立业务流程，合并一张表会产生大量空字段；拆分独立业务单据表，搭配通用审批流表统一管理多级审核。
4. **维修工单必须独立建表**
   报修工单包含维修人、维修费用、故障描述、维修进度等专属字段，无法合并至通用登记表。
5. **资产发票、设备照片需独立附件表**
   资产与附件为一对多关系，单独附件表统一存储文件路径、类型、上传人，易于后期扩展采购合同、验收单据等附件。
6. **缺失强制要求的审计日志表**
   实训需求明确要求所有操作实名留痕、可追溯，需新增全局操作审计日志表。
7. **缺失多人协同盘点专用数据表**
   本实训两大重点：多级审批、多人协同盘点，需新增盘点任务主表、盘点明细录入表，支持多人同时录入盘点数据、LLM自动比对盘盈盘亏。
8. **缺少通用数据字典表**
   资产状态、审批结果、资产分类等枚举统一由字典表管理，便于后期维护扩展。

#### 新增深度优化点（本次补充）
9. **盘点明细缺失去重约束，多人协同易产生脏数据**
   原盘点明细表未限制单任务下单资产的重复录入，多人并行盘点时易出现重复记录。优化：新增`(task_biz_id, asset_biz_id)`联合唯一约束，保证单任务下同一资产仅保留一条有效盘点记录。
10. **高频查询未覆盖软删除字段，索引回表开销大**
    所有业务查询默认携带`is_delete = 0`过滤条件，原索引未包含该字段，会导致查询时回表过滤。优化：将高频查询索引升级为联合索引，统一纳入`is_delete`字段，提升查询性能。
11. **部门树形查询无索引，多级部门查询性能差**
    `sys_department`表的`parent_biz_id`字段无索引，递归查询部门树时随数据量增长性能衰减明显。优化：为`parent_biz_id`新增普通索引。
12. **审计日志缺失业务关联维度，单资产追溯困难**
    原审计日志仅支持按操作人、模块查询，无法快速追溯单条资产/单据的全生命周期操作记录。优化：新增`business_type`、`business_biz_id`字段，关联对应业务主体，满足精细化审计追溯需求。
13. **资产编号与分布式ID耦合，适配性不足**
    原`biz_id`同时承担分布式ID和资产业务编号的职责，无法适配高校现有固定资产编码体系（国资编号、条码号）。优化：资产表新增独立`asset_code`业务编码字段，与biz_id解耦，支持自定义编码规则。
14. **部分枚举字段硬编码，扩展性不足**
    `attach_type`、`business_type`、`perm_type`、`user_status`等字段采用硬编码值，新增类型需修改代码。优化：建议全部枚举值逐步纳入`sys_dict`字典表统一管理，通过编码关联，降低维护成本。

#### SQLite专属适配调整
15. **数据类型适配**
    SQLite为动态类型系统，移除MySQL专属的`BIGINT`/`TINYINT`/`DECIMAL`等强类型，统一使用`INTEGER`、`NUMERIC`、`TEXT`，兼顾精度与兼容性。
16. **自增主键适配**
    MySQL的`BIGINT AUTO_INCREMENT`调整为SQLite标准的`INTEGER PRIMARY KEY AUTOINCREMENT`，保证主键自增特性。
17. **自动更新时间适配**
    SQLite不支持字段级`ON UPDATE CURRENT_TIMESTAMP`，`update_time`字段通过业务代码手动更新，或通过触发器实现自动刷新。
18. **引擎与字符集移除**
    删除`ENGINE=InnoDB`、`CHARSET=utf8mb4`等MySQL专属配置，SQLite原生支持Unicode字符集。
19. **外键约束可选开启**
    SQLite默认关闭外键约束，如需启用需执行`PRAGMA foreign_keys = ON;`，实训场景建议通过业务代码保障关联一致性。

## 二、统一数据库设计规范
### 2.1 主键规范（双ID设计，兼容分布式逻辑）
1. `id INTEGER PRIMARY KEY AUTOINCREMENT`：本地自增数字主键，用于单库快速关联查询；
2. `biz_id TEXT NOT NULL UNIQUE`：分布式唯一业务ID，雪花算法生成，接口、报表、业务交互统一使用。

### 2.2 约束标识说明
- PK：主键
- UK：唯一索引
- NK：NOT NULL 非空约束
- DEF：字段默认值
- FK：外键关联字段（关联对应表biz_id）
- COMMENT：字段注释

### 2.3 时间字段统一规范
1. 通用创建时间：`create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`
2. 通用更新时间：`update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`（需手动或触发器更新）
3. 业务专属时间：购置时间`buy_time`、申请时间`apply_time`、办结时间`finish_time`、盘点录入时间`check_time`、审批时间等。

### 2.4 软删除规范
所有业务主表统一增加字段：`is_delete INTEGER NOT NULL DEFAULT 0`，0=正常数据，1=逻辑删除，禁止物理删除，保障协同审计数据完整可追溯。

### 2.5 协同审计规范
所有业务操作、状态变更、盘点、审批记录均留存操作人`oper_user_biz_id`、操作时间，完整记录操作人员与操作行为；审计日志支持按业务主体追溯全生命周期操作。

### 2.6 SQLite 特殊规范
1. 索引统一使用`CREATE INDEX IF NOT EXISTS`单独创建，避免建表时语法兼容问题；
2. 文本类型统一使用`TEXT`，长度限制由业务代码控制；
3. 浮点金额使用`NUMERIC`类型，保证计算精度；
4. 自动更新时间推荐通过Python业务代码控制，复杂场景可搭配触发器。

## 三、完整SQLite数据表结构
### 模块一：系统组织架构与权限模块
#### 1.1 部门表 `sys_department`
存储学校、学院、实验室等多级部门信息
```sql
CREATE TABLE IF NOT EXISTS sys_department (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  biz_id TEXT NOT NULL UNIQUE,
  dept_name TEXT NOT NULL,
  parent_biz_id TEXT DEFAULT '',
  dept_sort INTEGER DEFAULT 0,
  is_delete INTEGER NOT NULL DEFAULT 0,
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_dept_parent ON sys_department(parent_biz_id);
CREATE INDEX IF NOT EXISTS idx_dept_is_delete ON sys_department(is_delete);
```

#### 1.2 角色表 `sys_role`
三级角色：超级管理员（校级）、学院资产管理员、普通师生
```sql
CREATE TABLE IF NOT EXISTS sys_role (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  biz_id TEXT NOT NULL UNIQUE,
  role_name TEXT NOT NULL,
  role_code TEXT NOT NULL UNIQUE,
  role_desc TEXT DEFAULT '',
  is_delete INTEGER NOT NULL DEFAULT 0,
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_role_is_delete ON sys_role(is_delete);
```

#### 1.3 权限表 `sys_permission`
存储后端接口URL、菜单按钮权限，用于角色权限绑定
```sql
CREATE TABLE IF NOT EXISTS sys_permission (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  biz_id TEXT NOT NULL UNIQUE,
  perm_name TEXT NOT NULL,
  perm_url TEXT NOT NULL UNIQUE,
  perm_type INTEGER NOT NULL,
  parent_biz_id TEXT DEFAULT '',
  is_delete INTEGER NOT NULL DEFAULT 0,
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_perm_parent ON sys_permission(parent_biz_id);
CREATE INDEX IF NOT EXISTS idx_perm_is_delete ON sys_permission(is_delete);
```

#### 1.4 角色-权限关联表 `sys_role_permission`
多对多中间表：一个角色绑定多个接口权限
```sql
CREATE TABLE IF NOT EXISTS sys_role_permission (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  role_biz_id TEXT NOT NULL,
  perm_biz_id TEXT NOT NULL,
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE(role_biz_id, perm_biz_id)
);
CREATE INDEX IF NOT EXISTS idx_rp_role ON sys_role_permission(role_biz_id);
CREATE INDEX IF NOT EXISTS idx_rp_perm ON sys_role_permission(perm_biz_id);
```

#### 1.5 用户表 `sys_user`
系统所有登录用户：管理员、师生，取消用户-部门中间表，直接存储所属部门
```sql
CREATE TABLE IF NOT EXISTS sys_user (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  biz_id TEXT NOT NULL UNIQUE,
  username TEXT NOT NULL UNIQUE,
  password TEXT NOT NULL,
  real_name TEXT NOT NULL,
  phone TEXT DEFAULT '',
  email TEXT DEFAULT '',
  dept_biz_id TEXT NOT NULL,
  user_status INTEGER NOT NULL DEFAULT 1,
  is_delete INTEGER NOT NULL DEFAULT 0,
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_user_dept_delete ON sys_user(dept_biz_id, is_delete);
CREATE INDEX IF NOT EXISTS idx_user_status ON sys_user(user_status);
```

#### 1.6 用户-角色关联表 `sys_user_role`
多对多中间表：支持一人分配多个角色
```sql
CREATE TABLE IF NOT EXISTS sys_user_role (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_biz_id TEXT NOT NULL,
  role_biz_id TEXT NOT NULL,
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE(user_biz_id, role_biz_id)

CREATE INDEX IF NOT EXISTS idx_ur_user ON sys_user_role(user_biz_id);
CREATE INDEX IF NOT EXISTS idx_ur_role ON sys_user_role(role_biz_id);
```

## 四、关键业务问题专项说明
### 4.1 维修工单是否需要独立建表？
**必须独立建表`fams_repair_workorder`**
1. 工单存在专属业务字段：维修人员、维修费用、故障描述、维修结果、工单流转状态，无法与领用、报废单据合并；
2. 工单需接入多级审批流程，独立表便于状态流转、维修台账统计、报表导出；
3. 若合并至通用登记表会产生大量空字段，降低查询性能，不利于后期扩展维修结算、耗材管理功能。

### 4.2 资产发票、凭证图片如何存储？
采用独立附件表`fams_asset_attach`一对多存储：
1. 单个资产可上传多张采购发票、设备实拍、报修截图；
2. 统一管理文件存储路径、文件类型、上传操作人员；
3. 资产主表不存储大文件路径，减少主表查询开销，可灵活扩展采购合同、验收单等附件类型。

### 4.3 分布式biz_id生成方案
所有业务对外ID（用户、资产、部门、单据、附件）统一使用32位字符串biz_id，推荐雪花算法生成，全局唯一；
- 数字自增id：仅用于数据库内部快速关联查询；
- biz_id：接口请求、前后端交互、报表导出、数据同步统一使用。

### 4.4 系统时间字段设计覆盖场景
1. 通用基础时间：`create_time`创建时间、`update_time`更新时间（全表标配）；
2. 资产基础时间：`buy_time`资产购置日期；
3. 审批流程时间：`apply_time`申请时间、`finish_time`办结时间、`dept_audit_time`学院审批时间、`school_audit_time`校级审批时间；
4. 资产借用时间：`borrow_start_time`借用起始、`borrow_end_time`预计归还、`actual_return_time`实际归还；
5. 工单业务时间：`report_time`报修提交时间、`finish_time`维修完成时间；
6. 盘点业务时间：`start_time`盘点开始、`end_time`盘点截止、`check_time`盘点录入时间；
7. 审计追溯时间：`oper_time`全局操作时间、资产状态变更记录时间。
全部时间字段完整覆盖实训需求中资产入库、领用、多级审批、多人协同盘点、报修报废全业务流程时间追溯。

### 4.5 SQLite 下 update_time 自动更新方案
SQLite 不支持字段级 `ON UPDATE CURRENT_TIMESTAMP`，提供两种落地方式：
1. **业务代码控制（推荐）**：Python执行UPDATE操作时，手动设置 `update_time = datetime.datetime.now()`，灵活可控，适配实训开发场景。
2. **触发器自动更新**：为每张业务主表创建UPDATE触发器，数据变更时自动刷新`update_time`，无需业务代码干预，适合对一致性要求高的场景。

### 4.6 多人协同盘点的数据一致性如何保障？
1. 通过`(task_biz_id, asset_biz_id)`联合唯一约束，从数据库层面杜绝单任务下重复盘点同一资产；
2. 所有盘点录入操作记录操作人与时间，支持多人并行录入且权责清晰；
3. 盘点任务状态与明细数据变更建议通过事务提交，避免任务状态与明细数据不一致。
